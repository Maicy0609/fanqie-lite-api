# 编程实现与代码维护原则

在现有项目中完成任务时，始终以**正确、简洁、可靠、易维护的最小改动**为目标。优先利用项目已有能力解决问题，避免不必要的依赖、重复实现和过度设计。

## 核心原则

1. **最小化修改（Minimal Changes）**：只修改完成当前需求所必需的代码，优先选择改动范围最小且语义清晰的实现。保留现有架构、接口、行为、依赖版本和项目约定。禁止无关重构、批量格式化、无必要的重命名或顺带添加功能。未经要求，不得擅自改变已有行为。

2. **优先复用，不重复造轮子（Reuse Before Reimplementing）**：编写代码前，优先检查项目现有实现、工具函数、框架 API、已安装依赖和语言标准库。能直接复用就不要重新实现；能调用成熟 API 就不要重复编写相同功能。尤其不要轻易手写加密、压缩、协议处理、复杂解析、数据库操作等底层或通用基础设施逻辑。

3. **严格控制依赖（Dependency Discipline）**：默认不引入新依赖。简单功能优先使用标准库、现有框架或项目已有依赖，避免仅为少量代码增加一个第三方包。只有当成熟的外部库能够带来明确的正确性、安全性或维护成本优势，且现有方案无法合理满足需求时，才考虑引入依赖。引入前应评估其维护状况、兼容性、体积、许可证及传递依赖，并选择满足需求的最轻量方案。

4. **单一职责与合理的文件组织（Single Responsibility）**：每个文件或模块应具有明确的主要职责。优先沿用现有目录结构和模块边界，将代码放在最合适的位置。只有在职责确实独立、分离能改善可读性或复用性时才新建文件。不要机械地拆分文件，不要为了形式上的单一职责制造大量小文件、无意义的包装层或重复抽象。

5. **简单优于复杂，清晰优于炫技（Keep It Simple）**：在满足需求的前提下，优先选择直接、易读、易调试、易维护的实现。避免过度工程化、过早抽象、重复封装、无实际用途的设计模式，以及针对假想需求预留的复杂扩展机制。不要为了减少代码行数而牺牲可读性、可靠性或必要的错误处理。

6. **尊重现有项目（Fit the Existing Codebase）**：修改前先检查与任务直接相关的代码、调用关系、配置和项目规范，理解现有实现后再动手。遵循项目已有的技术栈、编码风格和设计约定，不得为了偏好的技术方案而无必要地替换框架、重构架构或重写已有模块。调查范围应与任务规模相匹配。

7. **保证正确性，不以最小改动为借口**：最小化修改不等于拒绝必要的修改。若现有实现存在影响本次需求的缺陷，或最小补丁无法可靠满足需求，应采取必要的修正，并说明原因。不能为了减少代码、依赖或修改行数而引入安全隐患、数据损坏、兼容性问题或脆弱的实现。

8. **验证实际结果**：完成修改后，必须按照下方「完成标准」执行严格模式编译与全量冒烟测试。不要只为通过单个测试而硬编码结果、绕过检查或掩盖错误。任何验证结果都必须以实际执行情况为依据，不得虚报成功。

## 实施决策顺序

遇到多种可行方案时，优先考虑：

1. 复用项目现有实现或现有依赖；
2. 使用语言标准库或框架原生能力；
3. 在确有必要时，引入成熟、轻量且维护良好的第三方库；
4. 只有在没有合理的现成方案时，才自行实现必要的业务逻辑或基础功能。

如果简单方案已经能够可靠满足当前需求，不要为了抽象、通用性或未来扩展增加额外复杂度。

**原则优先级：正确性、安全性与兼容性优先，其次是最小化修改、合理复用、简洁性及长期可维护性。** 不要将任何一条原则机械地执行到损害整体质量的程度。

## 完成标准

**必须同时满足以下两项，才算任务完成：**

1. **严格模式编译通过**：使用当前项目技术栈所支持的最严格、合理且适用的编译配置完成全量编译，并确保相关类型检查、静态检查及严格模式校验全部通过。不得通过降低检查等级、关闭规则、屏蔽错误或修改配置来规避问题。
2. **全量冒烟测试全绿**：执行项目现有的全部冒烟测试，确保所有测试通过，覆盖本次修改涉及的核心功能及关键调用链。若现有测试不足以验证本次修改，应补充必要的冒烟测试。

两项均为强制门槛，不得以其中一项通过代替另一项。**任何编译错误、严格检查失败或冒烟测试失败，都意味着任务尚未完成。**

若检查或测试失败，应优先定位根因并进行最小化修复，然后重新执行完整的严格模式编译及全量冒烟测试，直至全部通过。不得只验证修改涉及的单个文件或仅运行部分测试便宣告成功。

如果受环境、依赖、权限或项目现有问题限制而无法完成全部验证，必须明确报告阻塞原因、实际执行的检查及其结果，不得虚报通过，也不得将未验证的任务标记为已完成。
